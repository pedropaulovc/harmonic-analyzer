## Why

A farm leaf failed 2026-09-17 on `swmaker000005@5`:

```
RuntimeError: logo ring extrude failed
  cad/scripts/diagnostics/diag_build_91247A720.py:337   # IFeatureManager.FeatureExtrusion3 -> None
```

and **passed on retry**, after the same part had been built and published
successfully twice earlier the same day. We are not accepting "flaky".

The logo ring was the one profile in the fleet deliberately authored *through*
the inference engine. Its own comment carried the reasoning:

```python
# Inference stays ON: exactly-coincident endpoints must merge into
# closed loops.  No endpoint radius (5.15-7.91) sits near a model
# silhouette (6.35/8.81/9.525), so the circle-snap hazard is absent.
```

Nine bare `CreateLine`/`Create3PointArc` calls, no relations, no closure check.
Whether those nine segments became two extrudable contours or nine loose curves
was decided by the seat.

**Both halves of that audit are unsound.**

1. **The clearance was measured in the wrong unit, and the seat variable has
   since been MEASURED.** Inference snapping has a screen-space tolerance â€”
   pixels, not millimetres â€” and nothing on the authoring path fits, orients or
   reads the view: the only `ViewZoomtofit2` / `ShowNamedView2` calls in the
   adapter are inside `export_image`, i.e. *after* the geometry exists.
   Authoring-time px/mm is inherited from the part template and the SolidWorks
   main-window size.

   `RootCause`'s verdict is now settled, and it names the variable: **the
   window**. The seat that failed was **1024x640**; the two that passed were
   **1296x816** â€” 1/0.620 of the area, so the failing seat resolved every
   millimetre into **0.62Ã— the pixels**. `RootCause` also measured a fitted view
   at 40â€“121 px/mm against a template view at 5â€“20 px/mm, with this profile's
   snap/no-snap crossover at roughly 12â€“20 px/mm; the fleet straddles it.
   `diagnostics/exp_inference_zoom.py` had already measured the dependence and
   it was never applied to the recipes.

   **Preference drift is REFUTED as the explanation**: zero divergence across 45
   preference names, and the failing seat had every snap toggle ON exactly like
   the two that passed. Nothing about that seat's *settings* differed; its
   *window* did.

   This is why the `AddToDB` direct-to-database path is the fix â€” **it removes
   the pixel term entirely.** No preference baseline could have prevented this
   failure. `SeatSettings`' fleet normalisation is still worth having (it closes
   the crashed-suppression latch, which is a real and separate defect), but it
   would not have saved this leaf.

2. **The wrong candidate set was audited.** Only *model* silhouettes were
   measured. That measurement is correct â€” 0.898 mm is really the tightest
   endpoint-to-silhouette margin â€” but the profile's own points are snap targets
   too, and this profile is adversarial. **Each inner-triangle vertex IS an
   outer corner arc's centre**, and arc centres are a first-class snap target
   (`swSketchSnapsCenterPoints`), so every outer arc endpoint has a competitor
   at exactly **0.400 mm**. At each corner that competitor is **three coincident
   targets** â€” the arc centre plus the two inner-triangle endpoints meeting
   there â€” against one correct merge partner at 0 mm, so the wrong answer has
   higher target density than the right one. Of the 24 snap targets in the
   profile (9 endpoints' worth, 3 arc midpoints, 3 arc centres), 15 pairs are
   exactly coincident and 69 more sit within 0.75 mm.

   0.75 mm is the number to compare against because **this codebase has already
   watched a snap fire at that distance**: a rectangle corner authored 0.75 mm
   off the origin snapped back to 0 with inference on and rebuilt the untrimmed
   shape with *no error at all*, caught only by a volume gate
   (`memory/solidworks-modeling-pitfalls.md:145-150`). So 0.400 mm is 0.53Ã— an
   observed firing distance and 2.25Ã— tighter than the margin that was audited
   and declared safe. That arithmetic is what makes the old comment's conclusion
   **unsound**, not merely unproven. If an outer arc endpoint takes the 0.4 mm
   snap to its own centre, the arc degenerates to zero radius and the outer
   chain stops being a loop â€” an extrude with no usable contour, which is
   exactly what the log shows.

   The ambiguity is **intrinsic**: the inner triangle must sit on the arc
   centres, because the inner offset degenerates (the centreline lines are
   tangent to the r=0.2 corner circles, so centreline âˆ’ 0.2 *is* the
   centre-to-centre edge). It cannot be nudged away by moving numbers. Explicit
   relations plus direct-to-DB authoring is the only fix that removes it.

Drawing that profile was a coin whose bias is the worker's window geometry.
Retrying it is playing the same coin again â€” which is why the retry "worked".

So the conclusion is not "normalise the setting". Normalising the setting is
necessary (`SeatSettings` is doing that, and it repairs the fleet) but it is not
sufficient, because a *normalised* seat with inference ON still has a px/mm term
in its geometry. **The dependency has to be removed from the recipes.** That is
this PR.

## What changed

### `cad/scripts/diagnostics/sketch_profile.py` (new â€” pure, no COM)

The profile algebra, so closure is a property of *coordinates* and is testable
offline:

- frozen `Line` / `Arc` (arcs are **centre + start + end**, never three points);
- `minor_arc(start, end, radius, *, ccw)` â€” derives the centre, refusing a
  semicircular span where the minor arc is not unique;
- `endpoint_merges(segments)` â€” pairs endpoints on **exact float equality** and
  refuses any vertex not shared by exactly two ends (a 3-way junction is
  `swSketchCheckFeatureStatus_e` 4 `ThreeEnts`, which we now reject offline);
- `closed_loops(segments)` â€” walks the merge graph and returns the loops;
- `OpenProfileError` carries the offending vertices.

### `diag_mcmaster_lib.draw_closed_profile(adapter, segments, *, label, loops)`

One authoring path for every closed profile, with inference **defeated twice**:

- segments are written **straight to the sketch database** (`AddToDB`) â€” the
  direct-to-DB path has no pixel term at all, and it is exactly the switch
  `exp_inference_zoom.py` flips to make snapping stop;
- ...*inside* a forced-preference block, so a seat whose preferences are hostile
  cannot reach the geometry by another route.

Then closure is **authored**, not inherited: one explicit relation per shared
vertex, each return value checked.

**`merge` (`swConstraintType_MERGEPOINTS`, 42), not `coincident` (9).** A merge
welds two endpoints into *one* point â€” which is what closure means, and what
inference itself would have done. Coincident leaves two distinct points held
together by a solver relation: the tolerant state we are trying to eliminate,
and it leaves `GetSketchPoints2` unable to tell a closed profile (9 points) from
an open one (18). `"merge"` is already in the adapter's `RELATION_NAME_MAP`
(`SolidworksMCP-python/.../sketch.py:35-37`), so no submodule change is needed.
Relations go through the adapter's `ISketchRelationManager.AddRelation` path
because `IModelDoc2.SketchAddConstraints` **silently no-ops** on SW 2026 /
3DEXPERIENCE (see the dead code removed from 99607A213 below).

A merge relation cannot be defeated by a view change: it is a solved constraint
in the document, not a pixel comparison made once at authoring time.

### Closure is asserted offline; the seat read-back is forensics

The closure **guarantee** is the offline assertion over the coordinates
(`endpoint_merges` / `closed_loops`, before any COM call) plus the explicit
merge relations, every one of which is checked as it is added.

The seat is *also* read once, and **exactly once**, after `exit_sketch`.
That read belongs to **`_common.record_sketch_closure`** (FailureForensics,
PR #773), which resolves the last profile feature's sketch, logs one uniform
line, emits a `sketch.closure` span event and returns a verdict. My half is
`assert_profile_closed(adapter, label, *, loops)`, which only decides the raise
from that verdict's **tri-state `closure`**:

- **`"closed"`** â€” contours exist. Accepted.
- **`"open"`** â€” the seat reported zero contours. That is a *measurement* of
  the exact failure mode this branch exists to prevent, so it raises.
- **`"unknown"`** â€” the read failed. The **absence of a measurement, not a
  measurement of absence**, so it must not raise: an RPC hiccup becoming a
  geometry failure would be a guard that fails closed on healthy geometry,
  which is worse than no guard.

A contour count that merely disagrees with `loops` also does not raise, because
it is still unmeasured whether 99607A213's revolve centreline (drawn into the
same sketch as its profile) registers as a contour. `record_sketch_closure`
warns; the build proceeds.

**Why one read and not two.** This branch first read
`ISketch.CheckFeatureUse(1, 0, 0)` itself, and had to guess the order of its two
counts â€” four of its twelve tests existed only to keep the guess from mattering.
Two independent readers of the same sketch can disagree, and when they do the
log line and the failure message stop being comparable, which is the entire
point of adding either. The authored **intent** is now recorded before drawing
(`_common.log_profile_geometry`: authored points, distinct places, expected
merges) and the seat's **outcome** once after; 91247A720 keeps the returned
verdict and feeds `contour_count` / `unmerged_points` straight into
`capture_com_failure`, so the extrude's failure context and the closure record
are literally the same numbers. The leaf that failed tonight recorded neither.

**The sketch is named, not guessed.** `record_sketch_closure` resolves an
unnamed sketch as caller dispatch -> named feature -> *last* `ProfileFeature`
-> `GetActiveSketch2`, and after `exit_sketch` there is no active sketch, so
the last-profile-feature branch answers. That is correct for a recipe that
authored one sketch and silently **wrong** for one that authored two before
checking. A verdict on the wrong sketch is worse than no verdict, so
`assert_profile_closed` *requires* the feature name both call sites have just
assigned (`LogoProfile`, `FlareProfile`).

**Where a collapsed corner is actually caught: offline, before any COM call.**
The nearest wrong snap target for an outer arc's endpoint is *that arc's own
centre*, 0.400 mm away, so the realised failure is an arc collapsed to zero
radius. Two gates catch that shape:

- `endpoint_merges` refuses any vertex not shared by exactly two segment ends;
- `minor_arc` refuses an endpoint that has **arrived at the centre**, by name,
  rather than catching it indirectly through a zero sweep out of `atan2(0, 0)`.

Both run on the coordinates. The seat read-back is **forensics and must not be
described as the guard** â€” it is deliberately incapable of failing
healthy geometry, so a collapsed corner would not reliably raise there.

**The ambiguity is intrinsic and must not be "fixed" by nudging coordinates.**
The inner triangle *must* sit on the outer arc centres: the centreline lines are
tangent to the r=0.2 corner circles, so centreline âˆ’ 0.2 *is* the
centre-to-centre edge. Explicit relations plus direct-to-DB authoring is the
only thing that removes it. That is written into the recipe so the next reader
does not try.

> `add_line_chain`'s docstring ("exact-coordinate endpoints still merge in the

> are written verbatim and coincide; a re-fitted 3-point **arc**'s endpoints are

### Seat poisoning â€” the reason this looked random *across* a fleet â€” a real defect, but NOT this failure's cause

`RootCause` refuted preference drift for the 2026-09-17 leaf (45 names, zero
divergence). The latch below is still a genuine fleet defect and is still fixed
here; it is simply not what broke the logo ring.


These sketch preferences are **application-level**. A leaf that dies inside a
suppression block leaves inference off for the rest of the seat's life. The old
save-and-restore-*observed* pattern made that **permanent**: the next leaf reads
the leaked value as "the original" and restores *it*.

- `no_sketch_inference` now restores a **declared** baseline
  (`SEAT_SKETCH_BASELINE`, all on) rather than what it observed;
- `assert_seat_sketch_baseline()` runs at recipe start in **both** entry paths
  (`run_replica()` and `_stock_fastener.build_stock_fastener()`), so a poisoned
  seat is repaired and the drift is *named* in the leaf log;
The latch leaks **across leaves**, not only within one: the toggles are
application-level and a seat outlives many leaves, so a leaf that died inside a
suppression block hours earlier leaves the next N leaves on that worker drawing
with inference off. "Self-inflicted inside one leaf" and "per-seat drift" are
the same mechanism at two timescales, not competing explanations, and the
declared-baseline restore fixes both. The recovered log shows the failing leaf
inheriting a warm seat, so carryover is the demonstrated path.

- two states are declared, not one: `SKETCH_DRAWING_STATE` (all off, what
  authoring wants) and `SEAT_SKETCH_BASELINE` (all on, what the seat must idle
  at). If the between-leaves baseline were the same object as the drawing state,
  a poisoned seat would read clean and the fleet repair would evaporate.

Preference **names** resolve through `solidworks_mcp` constants at runtime; no
hard-coded integers in the recipe layer. `SEAT_SKETCH_BASELINE` is the
harmonic-side mirror of the pool's `agent/seat_settings.py` `REQUIRED_TOGGLES`
and its comment names the pool as the source of truth.

Added **`swSketchInferFromModel` (95)** alongside `swSketchInference` (249) and
`swSketchAutomaticRelations` (9), on the evidence of this repo's *own* recorded
failure: `diag_build_93075A194`'s helix seed circle snapping to the shank
silhouette. That is inference from **model** geometry, which 249 does not
govern.

The whole **snap family is recorded** at recipe entry (`SKETCH_SNAP_AUDIT`,
`audit_sketch_snaps`) and never written â€” ids 266-280 read off the installed
`swconst.tlb` (R2026x) with `pythoncom.LoadTypeLib`, a type-library read that

They are recorded rather than applied for two reasons: they are ON by default,

That master-switch reading also sharpens the case for **95**: if 249 gates the

### Reentrancy

`no_sketch_inference` is now reentrant by depth count. This is a *consequence* of
restoring a declared baseline: an inner block exiting would switch inference
**ON** while the outer block is still drawing â€” strictly worse than the old
restore-observed code, which was accidentally immune. No nesting exists today
(checked lexically and through calls across all 15 files); one arc helper in
`diag_build_9275K141` keeps its inner guard deliberately, with a comment, so the
invariant is lexically visible at the primitive rather than implied by its
callers. The depth counter decrements unconditionally in `finally`.

Plus the **AST audit over every recipe file** — the regression gate for this
whole PR. It does not ask "was this primitive written inside a guard" but "was
a guard in force when it ran", which are different answers, so it walks
statements in order carrying the set of guarded **receivers**: a
`no_sketch_inference` block contributes *every* receiver (it forces application
preferences), an `AddToDB` try/finally contributes only its own, and each raw
call is matched against *its* receiver. Guards do not cross into deferred code
objects (`def`, `async def`, `lambda`, generator expressions), because those
bodies run later with the seat back at baseline; a class body is *not* deferred
and is deliberately excluded from that rule. Nine negative controls pin the
shapes that would otherwise be waved through: an unguarded primitive; a `try`
whose `finally` only assigns `AddToDB = False` (restoring a value it never
enabled, which a text search for `AddToDB` accepts); an intervening
`sk.AddToDB = False` before the block and one inside it; an enable of a
*different* receiver; a call on an unguarded receiver inside an otherwise
well-formed block; a raw primitive in the `finally` clause; and a primitive in
a nested function defined inside a guard — together with the positive controls
that the qualified spelling `diag.no_sketch_inference(...)` counts, that a
nested function carrying *its own* guard is clean, and that an `AddToDB`
enabled in an outer suite still guards a `try`/`finally` nested inside an `if`
or a loop -- state flows DOWN into nested suites by copy, so one branch cannot
enable a receiver for its siblings, and a disable flows back UP, so a branch
the walk cannot evaluate is assumed to have taken it. Plus a check that the
two exemptions
(`diag_cwm_min` / `diag_cwm_gear_min`, raw-COM minimal reproductions whose
*point* is unmediated calls) still exist and are still raw probes; they are
keyed by path *relative to* the diagnostics directory, since the walk is
recursive and a bare file name would also exempt a same-named file dropped
into any subdirectory.

**The gate is also audited for going quiet.** It walks `rglob`, not `glob`, so
a recipe moved into a subpackage cannot fall out of it silently, and it asserts
it inspected more than 20 files — a renamed directory would otherwise let the
whole gate pass having examined nothing. It accepts both
`no_sketch_inference(adapter)` and `diag.no_sketch_inference(adapter)`, because
reporting primitives inside a properly guarded block is how a gate gets
switched off. `CreateSplinesByEqnParams2` stays out of the audited set *by
recorded decision*: it takes an `ISplineParamData` (control points and knots,
no interactive point input) and the family is documented to ignore `AddToDB`
and write straight to the sketch database (cited at
`diag_build_1330K524.py:520`, `diag_build_9432K31.py:496`, both proven live),
i.e. it is permanently in the state `AddToDB = True` is used to reach.

## DEFERRED validation â€” what is NOT verified

No COM seat was taken and no farm leaf was dispatched: the farm is fully
occupied cutting release v36, and three workers hold hand-licensed seats the
release depends on. Everything above is offline-proven, read from the API

Unverified, in order of risk:

1. **Merge relations actually take on all 9 / 2 vertices**, via
   `ISketchRelationManager.AddRelation` with `"merge"`. Offline the relation set
   is provably right; that the adapter's name map reaches
   `swConstraintType_MERGEPOINTS` on a live sketch is unverified. This is the
   highest-risk item: if the relation silently fails, the remaining guarantee is
   the bit-exact coordinates plus `AddToDB`, which is better than tonight (no
   pixel term) but not what this PR claims.
2. **`AddToDB` + merge produces the same faces**, not merely the same solid.
   The first draft of this body said "same face *names* — downstream fillets
   select faces by name". That is wrong and I withdraw it: nothing in this repo
   selects a face by a name string. Every pick is geometric — `IFace2.GetBox`
   in the builders, a view XY coordinate pick through
   `_drawing_common.add_surface_finish` (its own parameter is `edge_xy`, and it
   documents itself as "widens a coordinate pick") in the drawings — and the
   selections inside `diag_mcmaster_lib` are by plane, solid body or feature
   name only. For these two parts specifically: `draw_knife_hanger_stud.py` and
   `draw_pen_set_screw.py` both go through `_purchased_fastener_drawing.py`,
   which authors views and notes with **no dimensions, no PMI and no
   face-attached annotations**, and `build_summing_assembly.py` places the studs
   by authored fixed transforms rather than face mates. So there is no stored
   face handle anywhere to go stale today.

   What *is* checked automatically: `gate_and_save` fails the build on volume
   (tol `max(0.02, v*2e-4)`), surface area (`max(0.10, v*5e-4)`), centre of
   mass, face **count**, and — when the vendor part has at most
   `FACE_MULTISET_LIMIT` (60) faces — the exact sorted face-area multiset,
   otherwise count plus the top `FACE_TOP_K` (30) areas. A solid that moved
   cannot ship. (Which branch 91247A720 takes is itself unverified offline: the
   face count comes from `cad/out/reports/mcmaster-91247A720-dump.json`, which
   is generated on a seat and is not checked in.)

   The gap the gate leaves is a solid that is geometrically identical while a
   reference *stored* against one of its faces no longer finds that face. A
   build cannot see that, and it becomes real the first time someone attaches
   a symbol to one of these faces. So this PR ships the probe that closes it
   rather than an argument: `probe_face_identity.py`.

   It splits the question in two, because one half can be answered offline and
   the other cannot, and mixing them produces a check that is wrong in both
   directions:

   - **Geometry** — `--diff` of two captured censuses: body and face extents,
     face areas, surface types, matched by geometry within tolerance (never by
     enumeration position: this part has three congruent grade marks and many
     identical fillet faces, so ties are the rule).
   - **Identity** — `--resolve`, which feeds the reference captured from the
     old part back through `GetObjectByPersistReference3` against the new one
     and checks three things: the state
     (`swPersistReferencedObjectStates_e`, a bitmask), that what came back is
     the same face, and that it is the same face **in its own body**. The last
     one is not pedantry here: the three grade marks are congruent separate
     bodies, so a reference that drifted to another mark's corresponding face
     matches on area, box and surface type, and without the owner check the
     probe would certify a broken reference. Owners are compared by extents,
     because a body's name comes from the feature that made it and this
     rewrite makes no promise about it.

   The first draft of the probe compared a *hash* of `GetPersistReference3` on
   both sides. That was wrong, and the API reference says so outright: "The
   internal representations of the return value array may change, possibly
   from rebuild to rebuild ... but their usage in finding the correct entity
   will be consistent across rebuilds and SOLIDWORKS releases." Byte
   inequality is therefore not a defect and byte equality is not a proof, so
   an ordinary rebuild could have reported every face as renumbered — and a
   probe that cries wolf on the part it was written for gets switched off,
   which costs the check as well. A digest also cannot be replayed, so it
   foreclosed the only honest test. The census now stores the complete
   reference (base64) and it never produces a verdict on its own: bodies
   whose extents tie are disambiguated by their sorted face **geometry**, so
   changed bytes cannot cause a mispairing, and a body that really did change
   a face still pairs on extents alone and gets diagnosed as such.

   Both comparisons are pure and tested offline
   (`cad/scripts/test_face_identity_diff.py`, 23 cases); what needs the seat
   is the capture and the replay.
3. **Whether construction geometry counts as a contour.** 99607A213 draws its
   revolve centreline into the same sketch as its profile, so a healthy one-loop
   flare may legitimately report two contours. Until that is measured, the
   `contour_count` may warn but may not fail a build; only a measured **zero**
   does. Settling it is what lets the check tighten from "raises when there are
   no contours at all" to "raises on the wrong contour count".
   (The old ambiguity about `ISketch.CheckFeatureUse`'s count ORDER is gone, not
   deferred: this branch no longer calls it. `_common.record_sketch_closure`
   owns the read and returns a tri-state verdict.)
4. **`swSketchInferFromModel` (95) is writable on `ISldWorks`.** All three
   toggles this PR asserts are documented there; the only two members
   `SeatSettings` found on `IModelDocExtension` are the rectangle pair, and
   both are excluded. Still worth a positive control on a seat.
5. **The 36 wrapped primitives** still produce their revolves and helices.
6. **That the two halves of the single-read contract agree on a live sketch** â€”
   `_common.record_sketch_closure` resolving the right sketch from the last
   profile feature, and `assert_profile_closed` reading its verdict. Signature
   agreement was verified offline against PR #773 with a local stub; the stub
   was reverted before commit, so on this branch alone the import fails until

    cad/out/reports/91247A720-faces-before.json \
    cad/out/reports/91247A720-faces-after.json

    --verdicts cad/out/reports/91247A720-resolve.json

Both seat modes go through `dodo._com_seat` and `run_build`, open one saved
part read-only, **build nothing**, and discard the document so they leave no
lock for the next leaf. Repeat with `99607A213-replica.SLDPRT`. A clean run
prints `N bodies: same geometry, face for face` and `N stored references all
resolve to their own face`; a `geometry:` line means the solid itself moved
(which `gate_and_save` would have failed first), and an `identity:` line means
a stored reference no longer finds its face, or finds a different one.

Two things in the replay are themselves unverified until it runs on a seat:
that pywin32 marshals the decoded reference back into the variant
`GetObjectByPersistReference3` expects, and that it hands back
`(object, state)` as a tuple. Both assumptions sit in `_persist_decode` and
`resolve_census`, and an answer the probe cannot read is recorded as "proves
nothing" rather than as a pass — so this mode can report that it failed to
ask the question, but it cannot silently answer it wrongly.
