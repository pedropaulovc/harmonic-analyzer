**Sharp edge RESOLVED via AutoMateRepair auto-heal — 2026-06-22, live seat.** The dangling-mate sharp edge (a geometry edit re-IDs the face a mate selected → REFRESH dangles it → previously fail-loud, manual `rm .SLDASM` + ~500s FULL re-mate) now **auto-heals in place**. Root cause confirmed: SW mates store PID snapshots of selected topology; a from-scratch part rebuild (`create_part` → new doc) regenerates the part's PIDs, so any mate that selected its faces dangles (What's-Wrong code **48** = entity not found). **`IAssemblyDoc.AutoMateRepair(out ProcessedMates, out FailedMates)` re-binds the broken mates by re-matching the still-present (re-IDed) entities** — the exact "entities present, mate broken" case it's built for.

EMPIRICAL PROOF (non-destructive, on the live 20-channel `channel.SLDASM`): rebuilt `pivot-shaft` from scratch (PID churn, identical geometry — its OD face is selected by coordinate via `bore_axis_ref(pivot_od)` in `build_channel_assembly.py`) → reopening channel dangled all **20 J1 rocker concentrics** (code 48). `AutoMateRepair` (after selecting the Mates folder) re-bound all 20 in **~5s**; post-rebuild What's-Wrong **0 faults**; DOF (144 comps fully-defined) + interference + deep-health gates all **PASS** → geometrically valid heal, not a silent mis-bind.

WIRED INTO `refresh_assembly` (`cad/scripts/_assembly.py`), helpers `select_mates_folder` / `repair_dangling_mates` / `_rebuild_faults`: per-config loop, on a non-warning fault → `repair_dangling_mates` → `ForceRebuild3` → re-read What's-Wrong; clean ⇒ fall through to the existing DOF/interference/health gates (the safety net against mis-heal); **STILL faulted ⇒ raise** (escalate to FULL). Three GOTCHAS, each load-bearing:
1. **Judge success by What's-Wrong + gates, NOT AutoMateRepair's return code.** It returns `PartialSuccess`(1) with a large `FailedMates` array (the assembly's *already-valid* mates it "can't re-repair" — 240 of them on channel) even on a fully successful heal. Treating ret==0/Success as the criterion would always escalate.
2. **Select the Mates folder first** (a `MateGroup` feature, the documented precondition). `SelectByID2("Mates","MATEGROUP",…)` did NOT work (returned False). `FeatureByPositionReverse(0..n)` finds it in a couple of COM calls — the MateGroup is the LAST top-level feature; a forward `FirstFeature` walk costs ~50s on 144 components (validated: heal dropped 56.8s→4.4s after switching to back-scan).
3. **A heal FORCES the in-place save** (`geometry_changed = prev != digest or repaired_any`): the re-bound mate PIDs MUST persist, or a PID-churn-only rebuild (identical geometry → unchanged mass-props digest → save skipped) re-dangles + re-heals the same mates on EVERY later refresh. Composes cleanly with the cascade fix — a no-op refresh (no dangle) still skips the save, so no spurious cascade. VALIDATED twice end-to-end: dangle→heal→gates→save (`channel.SLDASM` md5 changed, healed mates persisted), 2nd run with the fast selection healed in 4.4s. Remaining unknown (contained): if a churned PID silently re-resolves to a different-but-valid face (mate NOT flagged broken → AutoMateRepair skips it), the heal is a no-op but the DOF/interference/health gates still catch the geometric error and fail loud. This SUPERSEDES the earlier "auto-escalate REFRESH→FULL on cache-miss" proposal — heal-in-place (~5s) beats escalate-to-FULL (~500s).
