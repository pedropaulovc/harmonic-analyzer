**F5 pen driver — DE-RISKED (2026-06-16, throwaway `probe_pen_equation.py`).** The plan wants the pen-rod Y-travel mate equation-driven from a crank-angle global so the SW pose reproduces `truth_model.pen_y(θ) = magnify·Σ aⱼ·cos(j·θ+φⱼ)` (j=1..20) with NO force solver. Proven live on SW 2026:

- **SW equation manager REJECTS a single 20-term expression** (`set_global_variable`/`Add2` returns -1 → "Failed to add equation"). Not a syntax issue — diagnostic ladder showed global×global, `cos("Global")` (trig of a global, DEGREES), spaced/unspaced, and a 2-term sum ALL evaluate fine; the 20-term (708-char) sum fails both spaced and unspaced. **There is a length/term-count ceiling** (≥2 terms OK, 20 too many — exact boundary not probed).
- **FIX = chained partial-sum globals.** `S1 = a1*cos(1*"CrankDeg"+φ1)`, `Sk = "S{k-1}" + ak*cos(k*"CrankDeg"+φk)` for k=1..20, then `PenY = "Magnify" * "S20"`. Each link references only the prior partial + one new term → always short. Cover ALL 20 harmonics (not just nonzero) so an arbitrary coefficient vector still sums (plan F3).
- **Cascade re-eval works**: updating `CrankDeg` (in-place `Equation` put) re-solves the whole 20-deep chain transitively; re-reading `PenY` reflects it.
- **Matches `truth_model.pen_y` to FP precision** (worst |err| 7.95e-13 mm) at θ=0,30,45,90,137.5,200,270,333.3,360 — degrees-in-SW ≡ radians-in-Python by construction (`cos(j·θ_deg+φ_deg)` == `cos(j·θ_rad+φ_rad)`). Confirms the equation dialect + trig units.
- Tooling: `adapter.set_global_variable(SetGlobalVariableParameters(name, expression))`; `res.data["value"]` is the evaluated number. Globals must be declared in dependency order (Magnify, CrankDeg, then the chain). Precedent: [[harmonic-analyzer-project]] cone-gear equation globals.

**MATE-DRIVING DE-RISKED TOO (2026-06-16, throwaway `probe_pen_mate.py`, VERDICT SAFE).** User chose CrankDeg as a STANDALONE global in output.SLDASM (not linked to the real crank — testable in isolation, doesn't touch the validated top). Proven on a FRESH pen carriage (v-block+rod+marker, current geometry — the on-disk output.SLDASM is STALE so don't probe it):
- **output.SLDASM document units are INCHES (IPS).** Mate-dimension equations evaluate in DOCUMENT units, so `"D1@<mate>" = 398 + ...` set 398 INCHES (tip flew to 10079mm). FIX = read the mate's D1 right after creation (`Parameter("D1@<name>").Value` reads ~15.669 = 398/25.4 in doc units), compute `factor = base_doc/base_mm` (~1/25.4), and express base + scale in doc units. The pen tip still moves in physical mm. Same lesson as cone-gear "equations use document units".
- **Mate names DON'T survive the build label** — `distance_driver(label=...)` comes back auto-named `Distance5`. But `_mate()` RETURNS the dict, so `travel = await distance_driver(...); travel["name"]` gives the real name → drive `D1@<that>`. (Identifying it in a saved file by value/ref is unreliable; capture at creation instead.)
- **Display gain:** config coeffs are a math demo (square wave x80 → peak |pen_y| 682.64mm, unphysical), so map to a physical `PEN_STROKE_HALF_MM` (15mm chosen): `scale_mm = 15/peak`; PenScale(global, doc units) = `scale_mm*factor`. Default `CrankDeg=90` is the curve zero-crossing → mate==base → rest pose (tip 368) held EXACTLY. Tip follows `scale_mm*truth_model.pen_y` to 5.25e-05mm over 9 angles, fully-defined, no interference at ±15mm extremes.
